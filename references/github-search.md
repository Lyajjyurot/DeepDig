# 开源项目检索与贴合度评级

本文件在《需求确认清单》**被用户确认之后**才使用。

## 1. 提炼关键词

从清单中提炼 2~4 组查询，中英各至少一组。英文检索命中率显著更高。

**关键词来源**：核心对象（做什么）+ 形态（web/cli/extension）+ 关键机制（如 offline-first、multi-tenant）+ 技术栈。

**查询模板**（有 Web 搜索工具时）：

```
site:github.com "<核心对象英文>" <形态> stars:>100
site:github.com in:readme "<核心机制>" <技术栈>
site:github.com "<中文关键词>" <形态>
github awesome <领域> list
```

无搜索工具时，改写为 GitHub 站内搜索链接交给用户：

```
https://github.com/search?q=<关键词>&type=repositories&s=stars&o=desc
```

## 2. 筛选

按顺序过滤，最终只保留 **3~5 个**候选，不要堆一屏：

1. 许可证必须明确（无 LICENSE 的直接排除，或在卡片里标「许可证不明」并降级）；
2. 最近一次提交在 12 个月内，或 Star 增长仍在持续；
3. 核心对象一致（做同一件事），而不是「同一个技术栈做别的事」；
4. 已归档（archived）的项目只在无更好选择时保留，并注明。

**数据只写可核实的。** Star 数、语言、许可证读不到就写「未获取」，禁止凭印象编造数字。

## 3. 评级量表

逐项打分，满分 6：

| 维度 | 0 分 | 1 分 | 2 分 | 3 分 |
|---|---|---|---|---|
| 核心功能覆盖 | 只沾边 | 覆盖少数决策点 | 覆盖大部分决策点 | 完整覆盖清单主要决策点 |
| 技术栈一致 | 完全不同 | 部分可借鉴 | 主栈一致 | 主栈与形态完全一致 |
| 维护活跃度 | 归档/两年无提交 | 一年内有提交 | 半年内活跃 | 近 3 个月有提交且有 issue 响应 |

**评级映射**：

- **高**（5~6 分）：且核心功能覆盖 ≥ 2 分、技术栈一致 ≥ 1 分；
- **中**（3~4 分）：可以使用，但需要改造；
- **低**（0~2 分）：仅作参考，不建议复用。

**硬门槛**：核心功能覆盖为 0 或 1 分时，无论总分多少，最高只能评「中」。

## 4. 诚实性约束

- 评级服务用户决策，不服务于「显得有成果」。
- 不确定时往下调一级，并在「差异点」里写清不确定的地方。
- 只有一个候选且不够贴合时，宁可写「无高贴合」，也不要硬凑。
- 不要用「非常相似」「几乎一样」这类模糊措辞，用清单里的决策点逐条对照。

## 5. 复用询问

卡片列完后，用一段话收口：

> 以上 N 个项目中，我建议优先看 **{项目名}**，因为 {一句话：贴合清单中的 X 与 Y}；如果你更看重 {Z}，**{另一个项目}** 更合适。是否复用其中一个？还是都不复用、从零开始？

必须同时给出两条路径的代价：

- **复用**：能省什么（核心逻辑/UI/生态），要改什么（与清单冲突的决策点），引入什么成本（学习、依赖锁定、许可证义务）；
- **从零**：能省什么（无历史包袱、完全贴合），要付什么（重写核心功能的时间）。

## 6. 兜底

**没有任何「高」贴合**：

1. 明确输出「**未找到贴合度足够高的开源项目**」；
2. 列出最接近的 1~2 个，逐条说明差在哪：缺哪个核心功能、技术栈冲突在哪、维护状态如何；
3. 给出建议检索关键词，便于用户自己继续找；
4. 直接进入方案设计（本 Skill 到此结束，把已确认清单交给后续实现流程）。

**搜索无结果 / 无法联网**：

1. 直说当前环境无法完成检索，不要假装搜过；
2. 输出建议关键词与 GitHub 搜索链接；
3. 询问用户是否手动提供候选项目；用户提供后按第 3 节正常评级。
