# 决策树：建树、遍历与收敛

SKILL.md 只规定行为骨架，本文提供执行细则。全部为操作性说明，按需查阅。

## 1. 先判断需求形态

提问前先花 10 秒判断属于哪一类，这决定了建树的起点：

| 形态 | 判断信号 | 建树起点 |
|---|---|---|
| 全新项目（greenfield） | 空目录、无技术栈、无既有代码 | 从「范围与成功标准」开始 |
| 在既有项目上加功能 | 有代码库、有 README、有 package.json 等 | 先自己读代码，从「与既有架构的衔接」开始 |
| 重构 / 替换现有方案 | 已有实现但用户不满意 | 从「要保留什么、要丢掉什么」开始 |
| 只有一句话的模糊想法 | 无任何约束信息 | 从「给谁解决什么问题」开始 |

**事实自查清单（这些不要问，自己看）**：

- 目录结构、包管理器、框架版本、构建脚本；
- 已有 README / docs / 注释里的产品定位；
- 既有配置（`.env.example`、CI、lint、部署文件）；
- 已有数据模型、接口定义、目录命名习惯。

自查完仍不确定的，才是决策点。

## 2. 建树：把目标拆成决策点

默认分层（可裁剪，不必凑数）：

1. **范围**：这次做到哪一步？MVP 边界在哪？什么明确不做？
2. **用户与场景**：给谁用？在什么设备/环境下用？高频场景是哪一个？
3. **核心流程**：用户从头到尾走一遍的关键路径是什么？
4. **技术栈**：语言/框架/运行时；是否受团队或宿主环境约束。
5. **数据**：数据从哪来、存哪里、要不要迁移、隐私与权限。
6. **交付形态**：本地脚本 / Web / CLI / 插件 / 服务；怎么运行起来。
7. **非功能与边界**：性能、离线、多用户、成本、合规。

一个决策点只在满足**两个条件**时成立：

- 不同选择会导致明显不同的实现路径；
- 无法从环境或常识推定唯一答案。

否则不是决策点，别问。

## 3. 排序：深度优先 + 依赖优先

- 先问**会影响最多下游问题**的点（通常是范围与技术栈）。
- 依赖关系必须显式：上一问确定后才问下一问，并在话术中点明依赖。
- 反例：还不知道「要不要多用户」，就问「用哪种鉴权方案」。
- 用户提出新想法时，把新决策点挂到相关节点下，标记为「新增分支」，继续深度优先遍历，不推倒已确认的结论。

## 4. 三种归宿的判定

| 归宿 | 判定标准 | 写进清单的方式 |
|---|---|---|
| ✅ DECIDED | 用户明确选择，或用户授权按推荐执行 | 结论 + 一句可执行描述 |
| 🐇 RABBIT HOLE | 有价值但本次范围外；用户拒答；依赖未就绪 | 结论写「暂不做」，注明触发 v2 的条件 |
| ❌ NO-GO | 与已确认决策冲突、技术上不可行、成本/合规不可接受 | 结论写「排除」，**必须写原因** |

**没有第四种状态。** 悬而未决的问题不允许留在清单之外——要么继续问，要么归入 RABBIT HOLE 并写明风险。

## 5. 收敛判定

同时满足以下三条即可收口：

1. 每个可达分支都有归宿；
2. 清单里每一行都能被另一个工程师直接理解并执行；
3. 不存在「A 的答案会推翻 B」的隐性冲突（有就回到冲突点重问）。

收口后输出《需求确认清单》，**停下等用户确认**。确认前不搜索、不设计、不写代码。

## 6. 规模自检

| 情形 | 动作 |
|---|---|
| 问完 1~2 问就已无新决策点 | 说明需求已足够清晰，跳过追问，直接进入开源搜索 |
| 预计 3~8 问 | 正常遍历 |
| 到达第 8 问仍有未决点 | 必须收口：非关键未决点标 RABBIT HOLE 并写明风险；若剩余的是互不依赖的功能域，建议拆分后各跑一遍 |

**8 问是硬上限**，不因「看起来还差一点」而放宽。到第 8 问必须输出《需求确认清单》。提问前先排优先级（范围 > 技术栈 > 数据 > 形态 > 非功能 > 验收），确保这 8 问花在会改变实现路径的点上。

触发拆分建议的信号：树里出现了两个以上互不依赖的功能域（如「同时做后台管理 + 移动端 + 推荐算法」），或单个决策点无法用一句话回答完。

## 7. 反模式

- **问卷式轰炸**：一次性列出多个问题让用户填表 —— 违反一次一问。
- **伪选项**：三个选项其实都是同一方案，或没有「其他」。
- **问事实**：问用户「你项目用的什么框架」而仓库里写着 Next.js。
- **无限下钻**：在实现细节（变量命名、目录层级）上纠缠，这些不属于需求决策。
- **替用户拍板**：用户没选就把推荐项当结论写进清单；推荐只能用于「建议」，结论必须来自用户确认。
