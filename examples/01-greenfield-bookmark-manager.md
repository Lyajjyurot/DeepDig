## Agent

检索关键词：

- 英文：`self-hosted bookmark manager sqlite`、`bookmark manager web app tags search`
- 中文：`书签管理器 自托管 标签 搜索`

检索结果（按贴合度排序）：

**linkding** https://github.com/sissbruecker/linkding
Star：~8k｜语言：Python｜许可证：MIT
核心功能：自托管的轻量书签管理器，标签 + 全文搜索，提供 Web 界面。
贴合点：✅ 本地/自托管 Web 形态；✅ 标签与搜索；✅ 自带导入导出；✅ 单用户为主
差异点：Django 单体应用，与「轻量后端 + 主流前端」的设想不同；功能多于 MVP，裁剪成本存在
贴合度：**高**

**Karakeep（原 Hoarder）** https://github.com/karakeep-app/karakeep
Star：~17k｜语言：TypeScript｜许可证：AGPL-3.0
核心功能：带 AI 自动标签与全文抓取的书签/稍后读工具。
贴合点：✅ Web 形态；✅ 标签与搜索；✅ 技术栈现代
差异点：范围远超 MVP（AI 分类、抓取、多端）；AGPL 对分发有约束；部署依赖较多
贴合度：**中**

**Shiori** https://github.com/go-shiori/shiori
Star：~10k｜语言：Go｜许可证：MIT
核心功能：单文件部署的书签管理器，带离线归档。
贴合点：✅ 单机自托管；✅ 标签与搜索；✅ 部署简单
差异点：离线归档不在你的清单内；界面与交互偏旧；二次开发需要 Go 技术栈
贴合度：**中**

以上 3 个项目中，我建议优先看 **linkding**——它覆盖了你清单里的核心决策（本地 Web、标签、搜索、导出），MIT 许可证也最宽松。

- 复用的代价：需要裁掉不需要的功能，并接受 Django 技术栈；若你坚持「前后端分离」，改造成本会明显上升。
- 从零的代价：核心 CRUD + 搜索 + 导出大约是最容易写的部分，真正花时间的是界面打磨与数据迁移，复用能省下这部分。

是否复用 **linkding**？还是都不复用、从零开始设计？
